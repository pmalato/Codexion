# Codexion

## Description

Codexion is a C implementation of the classic **Dining Philosophers** synchronization
problem, reframed as coders sharing a limited pool of USB dongles in a co-working hub.

Each coder is represented by a POSIX thread that cycles through three states:
**compiling**, **debugging**, and **refactoring**. Compiling requires holding two
dongles at once (one on each side), and dongles are shared with neighboring coders —
so the program has to coordinate concurrent access to a limited resource, avoid
deadlocks, and make sure no coder "burns out" from not compiling often enough.

The simulation stops either when every coder has compiled at least
`number_of_compiles_required` times, or when a coder burns out.

## Instructions

### Compilation

```bash
make
```

This builds the `codexion` binary using `cc` with the `-Wall -Wextra -Werror -pthread`
flags, following the project's Makefile rules (`all`, `clean`, `fclean`, `re`).

### Usage

```bash
./codexion number_of_coders time_to_burnout time_to_compile time_to_debug \
	time_to_refactor number_of_compiles_required dongle_cooldown scheduler
```

| Argument | Description |
|---|---|
| `number_of_coders` | Number of coders (and dongles) |
| `time_to_burnout` | Time (ms) before a coder burns out without compiling |
| `time_to_compile` | Time (ms) spent compiling |
| `time_to_debug` | Time (ms) spent debugging |
| `time_to_refactor` | Time (ms) spent refactoring |
| `number_of_compiles_required` | Compiles needed per coder before the simulation stops successfully |
| `dongle_cooldown` | Time (ms) a dongle stays unavailable after being released |
| `scheduler` | Dongle arbitration policy: `fifo` or `edf` |

Example:

```bash
./codexion 5 600 200 200 200 10 0 fifo
```

All arguments are mandatory and validated; invalid input (negative numbers,
non-integers, or an unrecognized scheduler) causes the program to exit safely.

### How AI was used

AI (Claude) was used strictly as a debugging and code-review assistant, never as a
code generator. All design decisions, data structures, and implementation were written
from scratch independently. AI was consulted for:

- Interpreting `Helgrind` output and pinpointing the exact lock-order inversion between
  the dongle mutexes and coder mutexes (in `dongle_acquire`/`edf` vs. `check_burnout`).
- Reviewing already-written code to identify two unprotected shared-memory accesses
  (`alive` and `deadline` read outside their mutex) flagged by `Helgrind` as data races,
  and confirming the fix approach (reading/writing shared fields only under their
  owning mutex, and caching the result in a local variable to avoid re-reading).
- Drafting this README structure and wording, based on the project's requirements.

No function body, algorithm, or line of program logic was generated by AI; all fixes
were written and applied by hand after understanding the reasoning behind them.

### Blocking cases handled

- **Hold-and-wait elimination (deadlock prevention):** Originally a coder acquired
  its left dongle, then blocked while still holding it waiting for the right
  dongle — one of Coffman's four necessary deadlock conditions. `acquire_pair`
  removes this: a coder registers intent on both dongles, then only ever commits
  to taking them at the instant *both* are simultaneously free and it's at the
  head of both queues. If that's not the case, both locks are released before
  waiting — the coder holds nothing while blocked.
- **Consistent lock ordering:** the two dongles are always locked in the same
  global order (lower coder id first, via `cond_swap`), so no circular wait can
  form even though both mutexes are held briefly during the readiness check.
- **Starvation prevention:** FIFO/EDF queue position is checked as part of
  readiness, so a coder can't repeatedly "cut in line" ahead of one who
  registered earlier / has an earlier deadline.
- **Cooldown handling:** readiness also requires both dongles to be past their
  post-release cooldown.
- **Precise burnout detection:** unchanged — the monitor thread polls every
  500µs and prints the burnout log within that bound.
- **Log serialization:** all state-change prints go through `safe_print`, which
  holds a single mutex for the duration of the `printf`, so lines never interleave.

## Thread synchronization mechanisms

- **`pthread_mutex_t` per dongle:** protects each dongle's `state`, `queue`, and
  `cooldown` fields. Every acquisition/release of a dongle happens under this lock,
  preventing two coders from taking the same dongle simultaneously.
- **`pthread_cond_t` per dongle:** used in `dongle_acquire` so a coder waiting for a
  dongle sleeps on the condition variable instead of busy-waiting, and is woken via
  `pthread_cond_broadcast` whenever a dongle is released or the monitor needs to check
  on a waiting coder (`dongle_broadcast`).
- **`pthread_mutex_t` per coder:** protects each coder's shared state (`deadline`,
  `alive`, `done`). Both the coder's own thread (`compile()`) and the monitor thread
  (`check_burnout`, `is_program_over`) read/write these fields exclusively through this
  lock, via small getter helpers (e.g. `get_coder_deadline`, `get_coder_alive`) that
  copy the value into a local variable before releasing the lock — avoiding both data
  races and unnecessarily long critical sections.
- **Global lock ordering:** to avoid deadlock between the coder and dongle locks, the
  program follows a strict rule: a coder mutex is never held while trying to acquire a
  dongle mutex (or vice versa). Concretely, `check_burnout` reads/updates coder state
  under the coder's mutex, releases it, and only then calls `dongle_broadcast`,
  ensuring the coder → dongle nesting from earlier revisions no longer exists.
- **`main_lock`:** a single mutex protecting the shared `stop` flag in `t_arguments`,
  allowing any thread to request a global stop (`request_stop`) and any thread to check
  it (`check_stop`) safely.
